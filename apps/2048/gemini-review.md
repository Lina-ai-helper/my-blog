# 2048 게임 웹앱 — 추가 Review 결과

> 기존 review.md와 HTML/CSS/JS를 대조한 독립적인 코드 레벨 검토다.
> 기존에 문서화된 사항은 제외하고, 추가로 확인한 문제만 기록했다.
> 실제 브라우저·보조공학 동작 검증은 수행하지 않았다.

## 1. 접근성

- **보드의 행·열·빈 칸 정보가 전달되지 않음**
  - 위치: `game.js:41–56` — `renderBoard()`, `index.html:33`.
  - 타일은 일반 div의 숫자 텍스트로만 생성되며, 빈 칸에는 텍스트가 없다. 행 구분이나 좌표 설명도 없어 스크린리더 사용자가 숫자의 실제 위치와 빈 공간을 파악하기 어렵다.
  - 기존 점수/승리 안내와 별개로, 다음 이동을 판단하는 데 필요한 보드 정보가 부족하다. 각 칸의 좌표·값·빈 칸 여부를 읽을 수 있는 표현이 필요하다.

## 2. 엣지 케이스

- **승리 오버레이가 표시되어도 방향키로 게임이 계속 진행됨**
  - 위치: `game.js:122–137` — `handleMove()`, `game.js:166–173` — 키보드 입력.
  - 이동 차단 조건은 상태 미생성과 게임 오버뿐이다. 승리 오버레이가 열려 있어도 방향키가 전역 핸들러를 통해 보드를 변경한다.
  - 사용자가 '계속하기'를 선택하기 전에 타일과 점수가 바뀌며, 추가 이동으로 게임 오버가 되면 승리 화면이 게임 오버 화면으로 교체될 수 있다. 승리 후 계속하기 선택 전에는 이동을 막아야 한다.

- **저장 실패 환경에서는 새 게임 시작 시 세션 내 최고 점수도 사라짐**
  - 위치: `game.js:83–101` — `newGame()`·`updateBestScore()`, `storage.js:7–24`.
  - 저장 예외는 무시하지만 최고 점수는 메모리에서 갱신한다. 이후 새 게임은 그 값을 유지하지 않고 저장소에서 다시 읽는다.
  - 저장소 접근이 막히면 0으로, 읽기는 가능하나 쓰기가 실패하면 과거 저장값으로 되돌아간다. 영구 저장 실패와 별개로 현재 세션의 최고 점수는 유지할 필요가 있다.

## 3. 성능 및 렌더링

- **이동할 때마다 그대로인 타일까지 팝인 애니메이션이 재시작됨**
  - 위치: `game.js:41–56` — `renderBoard()`, `style.css:189–200`.
  - 보드를 비우고 모든 타일을 새 DOM으로 생성하기 때문에 새로 생기거나 병합된 타일뿐 아니라 기존 타일에도 애니메이션이 다시 적용된다.
  - 빠른 연속 입력에서는 보드 전체가 반복적으로 축소·확대되어 이동 결과를 추적하기 어렵다. 16칸 규모에서 심각한 성능 저하를 단정할 수는 없으나, 불필요한 DOM 재생성과 애니메이션은 명확하다.
  - 셀을 재사용하고 생성·병합된 타일에만 애니메이션을 적용하는 방식이 적절하다.

## 4. 수정 여부

네 가지 지적 모두 타당하다고 판단해 반영했다 (`game.js`, `style.css`).

- 보드 좌표/빈 칸 정보 없음 → 각 `.cell`에 `aria-label`("N행 M열, 값/빈 칸")을 추가.
- 승리 오버레이 중 이동 가능 → `handleMove()`에 `state.won && !state.keepPlayingAfterWin` 차단 조건 추가.
- 저장 실패 시 세션 내 최고 점수 손실 → `newGame()`에서 `Math.max(loadBestScore(), state?.best ?? 0)`로 세션 최고 점수를 유지.
- 정지한 타일까지 팝 애니메이션 재생 → 렌더링 직전 격자를 스냅샷해두고, 이전과 같은 위치·값이면 `tile--static` 클래스로 애니메이션을 끔. 단, 타일 ID를 추적하지 않으므로 "다른 칸에서 밀려와 값이 그대로인 타일"은 여전히 애니메이션된다(완전한 타일 추적 리팩터링은 범위를 벗어난다고 판단).
