# 2048 게임 웹앱 — 계획 (spec)

> 상태: **Plan 단계 산출물**. 이 문서는 계획서이며, 이 시점까지 구현 코드는 작성하지 않았다.
> 저장소 루트 `CLAUDE.md`의 기술 원칙(프레임워크/외부 라이브러리 금지, 빌드 도구 없음, 모던 표준 사용)을
> 그대로 따르되, 이 앱은 블로그 본체와 분리된 독립 미니앱으로 `apps/2048/` 안에 자체 완결된다.

## 1. 게임 개요 및 주요 기능

4x4 격자에서 방향키(또는 모바일 스와이프)로 타일을 한 방향으로 밀면, 같은 숫자 타일끼리 부딪힐 때 합쳐지며
점수가 올라가는 퍼즐 게임. 순수 HTML/CSS/JS(Vanilla, ES Modules)로 구현하고 외부 라이브러리는 쓰지 않는다.

주요 기능 목록:

- 4x4 격자 렌더링 및 타일 이동/병합 애니메이션(간단한 CSS transition 수준)
- 키보드 방향키(↑↓←→) 조작
- 모바일 터치 스와이프 조작 (touch 이벤트 기반, 별도 버튼 UI 없이 스와이프 제스처만 지원)
- 이동/병합 후 빈 칸 중 무작위 위치에 2(90%) 또는 4(10%) 타일 생성
- 현재 점수 표시 및 병합 시 점수 누적
- 최고 점수(best score) `localStorage` 저장 및 새로고침 후에도 유지
- "새 게임" 버튼으로 언제든 초기화
- 2048 타일 최초 등장 시 승리 오버레이 표시 — 단, "계속하기"를 선택하면 게임을 이어서 플레이 가능
- 더 이상 이동도 병합도 불가능하면 게임 오버 오버레이 표시
- 반응형 레이아웃 (모바일 우선, 가로 스크롤 없음)
- 키보드 포커스 및 기본적인 스크린리더 대응(점수/게임 상태를 aria-live로 안내)

범위에서 제외하는 것(이번 계획의 비범위):
- 실행 취소(undo), 온라인 랭킹, 사운드, 테마(다크모드) 전환 — 필요해지면 별도 계획에서 다룬다.

## 2. 파일 구조

```
apps/2048/
├── index.html     # 게임 페이지 뼈대: 헤더(점수판, 새 게임 버튼), 격자 컨테이너, 오버레이 마크업
├── style.css      # 이 앱 전용 스타일 (자체 CSS 변수 팔레트, 반응형 레이아웃, 타일/오버레이 스타일)
├── game.js        # 진입점(ES Module): 이벤트 바인딩(키보드/터치/버튼)과 렌더링-상태 연결(오케스트레이션)
├── board.js       # 격자 상태 표현, 이동/병합 순수 로직(방향별 slide+merge), 랜덤 타일 생성, 승리/게임오버 판정
├── storage.js     # localStorage 읽기/쓰기 래퍼 (최고 점수 저장/조회)
└── spec.md        # 이 계획 문서
```

파일을 이렇게 나누는 이유: `board.js`는 DOM에 의존하지 않는 순수 로직(테스트하기 쉽고, CLAUDE.md가 강조하는
"작은 함수, 한 가지 일"을 지키기 위함)으로, `game.js`는 DOM/이벤트 처리 전담으로, `storage.js`는 저장소
접근을 한 곳에 모아 나중에 키 이름이 바뀌어도 영향 범위를 좁히기 위해 분리한다.

## 3. 핵심 로직 설계 요약

### 격자 상태 표현
- 4x4 숫자 배열을 1차원 배열(길이 16) 또는 2차원 배열(4x4) 중 **2차원 배열(`number[4][4]`)** 로 표현한다.
  빈 칸은 `0`으로 표기한다. 2차원 배열이 "행/열" 개념과 1:1 대응되어 이동 로직을 읽기 쉽게 만든다.
- 상태 객체 예시(설명용, 실제 타입은 구현 시 확정): `{ grid: number[4][4], score: number, best: number, won: boolean, over: boolean, keepPlayingAfterWin: boolean }`
- 각 타일에는 렌더링 시 고유 식별자(예: 생성 순번 기반 id)를 부여해 CSS transition으로 이동을 자연스럽게
  표현할 수 있게 한다(선택적 개선 사항 — 최소 구현은 매 이동마다 격자를 다시 그려도 무방).

### 이동/병합 알고리즘 개요
- 방향은 4가지(위/아래/왼쪽/오른쪽)이지만, 내부적으로는 "왼쪽으로 밀기" 한 가지 핵심 함수(`slideRowLeft`)만
  구현하고, 다른 방향은 격자를 회전/반전시킨 뒤 같은 함수를 적용하고 다시 되돌리는 방식으로 재사용한다.
  (2048 구현에서 흔히 쓰는 방식으로, 중복 코드를 줄이고 "함수는 작고 한 가지 일만" 원칙에 맞는다.)
- 한 행에 대한 왼쪽 밀기 처리 순서:
  1. `0`이 아닌 값만 왼쪽으로 압축(빈 칸 제거)
  2. 왼쪽부터 순서대로 인접한 두 값이 같으면 병합(합산), 병합된 칸은 그 턴에 다시 병합되지 않도록 표시
  3. 병합 후 점수에 합산값 더하기
  4. 다시 왼쪽으로 압축해 길이 4로 맞춤
- 이동 발생 여부(격자가 실제로 바뀌었는지) 를 반환값으로 함께 넘겨, 변화가 없으면 새 타일을 생성하지 않는다
  (2048에서 "움직이지 않았는데 타일이 생기는" 흔한 버그를 방지).

### 새 타일 생성
- 이동 후 격자가 바뀐 경우에만, 빈 칸(`0`) 좌표 목록에서 무작위로 하나를 골라 2(확률 90%) 또는 4(확률 10%)를 채운다.

### 게임 종료 판정
- 승리: 격자 안에 `2048` 값이 처음 등장하면 승리 오버레이를 띄운다. 이후에도 격자 상태는 유지되며
  "계속하기"를 누르면 오버레이만 닫고 게임을 계속한다(같은 판이 게임오버 될 때까지 재도전 가능).
- 게임 오버: 빈 칸이 없고, 동시에 가로/세로 어느 방향으로도 인접한 두 칸이 같은 값이 아니면(즉 어느 방향으로
  밀어도 변화가 없으면) 게임 오버로 판정한다. 실제 구현에서는 4방향에 대해 "이동 가능 여부"만 가볍게
  시뮬레이션(격자를 실제로 바꾸지 않고 판정)해서 확인한다.

### 점수 계산
- 두 타일이 합쳐질 때마다 합쳐진 결과값(예: 2+2=4가 되면 4점)을 현재 점수에 더한다.
- 현재 점수가 저장된 최고 점수보다 커지는 순간 최고 점수도 함께 갱신하고 저장한다.

### localStorage 키
- `2048-best-score` — 최고 점수(숫자, 문자열로 직렬화)를 저장하는 단일 키.
- 현재 진행 중인 판(격자 상태) 저장은 이번 계획의 범위에 포함하지 않는다(새로고침 시 새 게임으로 시작).
  필요성이 제기되면 `2048-game-state` 같은 별도 키로 후속 계획에서 추가한다.

## 4. UI/디자인 개요

- 이 앱은 블로그 본체와 분리된 독립 미니앱이므로, 블로그의 색 변수 체계를 그대로 따르지 않고
  **자체 CSS 변수 팔레트**를 `apps/2048/style.css`의 `:root`에 정의한다. 다만 CLAUDE.md의 디자인 원칙
  (색은 절제해서 사용, 그림자/애니메이션 최소화, 모든 색은 변수로 정의하고 하드코딩 금지)은 그대로 지킨다.
- 팔레트 방향: 배경은 따뜻한 베이지/크림 계열, 격자 보드는 짙은 회갈색, 타일은 숫자 값이 커질수록
  진해지는 오렌지~골드 그라데이션 단계(2048 원작 느낌을 참고하되 그대로 베끼지 않는 자체 색상표를 정의).
  다크 모드는 이 계획 범위에서는 필수로 넣지 않는다(별도 앱이라 블로그 테마 토글과 무관하며, 필요 시
  후속 계획에서 `prefers-color-scheme` 기반으로 추가할 수 있음).
- 레이아웃: 모바일 우선. 상단에 제목 + 점수판(현재 점수 / 최고 점수 두 개의 박스) + 새 게임 버튼을
  한 줄 또는 두 줄로 배치. 그 아래 정사각형 4x4 보드를 뷰포트 너비에 맞춰 `aspect-ratio: 1 / 1`과
  `min()`/`clamp()`로 크기를 제한한다. 보드는 `display: grid`(4x4)로 구성하고 타일 간 일정한 간격(gap)을 둔다.
- 타일: 둥근 모서리, 숫자 크기는 자릿수에 따라 약간 줄어들게(예: 4자리 이상이면 폰트 축소) 처리해 넘침을 방지.
- 애니메이션: 타일 등장 시 살짝 확대되는 팝인, 이동 시 위치 이동은 `transform` transition(150~200ms)
  정도로 짧고 절제되게. `prefers-reduced-motion: reduce`일 때는 transition을 없앤다.
- 오버레이(게임 오버/승리): 보드 위에 반투명 배경 + 중앙 메시지 카드로 표시하며, 버튼(다시 시작 / 계속하기)을 포함.

## 5. 키보드/터치 조작 방식

- 키보드: `keydown` 이벤트에서 `ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`를 감지해 해당 방향으로 이동
  처리. 페이지 스크롤을 막기 위해 방향키 입력 시 `preventDefault()`를 호출한다. 포커스가 버튼 등 다른
  요소에 있어도 문서 전역에서 키 입력을 받도록 `document`에 리스너를 둔다.
- 터치(모바일 스와이프): 보드 영역에서 `touchstart`의 시작 좌표와 `touchend`의 종료 좌표 차이를 계산해,
  이동 거리가 일정 임계값(예: 20~30px) 이상이면서 수평/수직 중 더 크게 움직인 축을 기준으로 방향을 판정한다.
  화면 스크롤과 스와이프 제스처가 충돌하지 않도록 보드 영역에서는 `touch-action: none` 또는 `preventDefault`로
  세로 스크롤 간섭을 막는다.
- 별도의 방향 버튼(온스크린 D-pad)은 최소 구현 범위에는 포함하지 않는다. 지침에 명시된 "모바일용 스와이프
  선택"에 따라 스와이프만 지원하며, 접근성 보완은 6장의 키보드 포커스/스크린리더 안내로 대신한다.

## 6. 접근성 고려사항

- **색약자 대응**: 타일 구분을 색상 하나에만 의존하지 않는다. 모든 타일에 숫자가 항상 표시되므로 색맹이어도
  값 구분이 가능하다. 추가로 타일 배경색과 숫자색의 명도 대비를 WCAG AA(4.5:1) 이상으로 맞추고(특히 밝은
  배경의 저숫자 타일과 진한 배경의 고숫자 타일 모두 확인), 색상 단계가 밝기 순서로 단조롭게 증가하도록
  설계해 "색이 아니라 숫자와 밝기로도" 값 크기를 유추할 수 있게 한다.
- **키보드 접근성**: "새 게임" 버튼, 오버레이의 "다시 시작"/"계속하기" 버튼 모두 `<button>` 요소로 만들어
  기본적으로 Tab 포커스와 Enter/Space 실행이 가능하게 하고, `:focus-visible` 스타일(윤곽선 등)을 CSS로
  명시한다. 게임 조작 자체(방향키 이동)는 별도 포커스 없이 문서 전역에서 동작하므로 키보드만으로 전체
  플레이가 가능하다.
- **스크린리더/상태 안내**: 점수판 영역 또는 별도의 시각적으로 숨겨진(`sr-only` 방식) 영역을
  `aria-live="polite"`로 두어 "점수 변경", "게임 오버", "2048 달성" 같은 상태 변화를 안내한다. 오버레이에는
  `role="alert"` 또는 `aria-live="assertive"`를 사용해 게임 종료/승리 시점을 즉시 알린다.
- **모션 최소화**: `prefers-reduced-motion: reduce` 미디어 쿼리를 존중해 타일 팝인/이동 transition을
  비활성화하거나 최소화한다.
- **터치 타깃 크기**: "새 게임" 버튼 등 상호작용 요소는 최소 44px 높이를 확보해 모바일에서 누르기 쉽게 한다.
- **이미지/아이콘**: 이 앱에는 장식 이상의 의미 있는 이미지가 없을 것으로 예상되나, 아이콘을 추가할 경우
  장식용은 `aria-hidden="true"`, 의미가 있는 경우 `alt`/`aria-label`을 붙인다.
